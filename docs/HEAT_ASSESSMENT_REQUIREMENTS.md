## 一、背景与目标

### 1.1 现状

App 目前只记录**热量摄入**（DietRecord）和**目标热量**（targetDailyCalories），没有任何"消耗"数据，因此：

- 无法计算真正的热量缺口 / 冗余（吃进去的 vs 消耗掉的）；
- AI 每日评估只能基于"摄入 vs 目标"，看不到运动消耗，评估维度不完整；
- 对话 Agent 也无法回答"我今天消耗了多少"这类问题。

### 1.2 目标

接入小米手环 7 的**心率广播**（标准 BLE 心率协议，无需小米官方 SDK），实时读取运动心率，估算运动消耗，结合基础代谢（BMR），构建完整的每日热量评估：

**净摄入 = 摄入 − 运动消耗**
**热量缺口/冗余 = 目标热量 − 净摄入**

### 1.3 范围界定

**本期做（2026-08-06 确认范围）：**

- 档案补充年龄、性别字段（BMR 与心率公式必需）；
- 系统步数读取（硬件计步传感器，非 Google 服务）；
- GPS 户外运动记录（跑步 / 骑行 / 步行，前台服务采集轨迹）；
- 运动消耗自动记录（GPS 运动 + 步数估算）+ 手动补录；
- 看板热量卡片升级（摄入 / 运动消耗 / 净摄入 / 缺口）与步数展示；
- AI 每日评估与对话 Agent 注入消耗 / 步数数据；
- Room 新增运动记录表与每日步数表。

**本期不做：**

- 轨迹地图可视化（GPS 数据先入库，地图展示后置，避免引入高德/百度 SDK 依赖）；
- **米环 7 心率接入（BLE）延期**：需求已评审，本期不实现，待后续阶段开工（见 FR2）；
- 厂商 SDK / 穿戴历史数据同步（小米运动健康 App 内的历史记录无法直接读取）；
- Health Connect / Google Fit（国内设备无 Google 服务，适配度低）。

## 二、功能需求

### FR1 用户档案补充

- 档案新增：**年龄（岁）**、**性别（男/女）**。
- 入口：现有训练档案编辑弹窗（Dashboard 与训练计划页共用）中增加两个字段。
- 默认值：年龄 25，性别男；用户修改后 DataStore 持久化。
- 热量计算时读取档案值；未填写时使用默认值并在结果页标注"估算基于默认档案"。

### FR2 米环 7 心率连接（核心，⚠️ 本期延期）

> 状态：已评审，本期不实现。恢复开发时按以下设计执行。

#### 2.1 连接方式

- 使用 Android 系统 BLE API（BluetoothLeScanner / BluetoothGatt），遵循标准 Heart Rate Profile：
  - 服务 UUID：`0000180d-0000-1000-8000-00805f9b34fb`
  - 心率特征：`00002a37-0000-1000-8000-00805f9b34fb`（Notify）
  - 解析：Flags + 心率值（uint8 / uint16）
- 不需要小米 SDK、不需要小米账号。

#### 2.2 交互流程

1. 用户在"运动记录"页点击"开始心率记录"；
2. App 检查蓝牙与相关权限，未授权则引导授权；
3. App 展示引导弹窗：**请在手环端开启"心率广播"**（手环设置 → 心率广播），说明开启方法；
4. App 扫描附近 BLE 设备（按服务 UUID 过滤），自动连接米环 7；
5. 连接成功后显示实时心率、心率区间、已计时长、累计消耗；
6. 用户点击"结束"，生成一条运动记录并入库。

#### 2.3 保活与稳定性

- 心率记录期间运行**前台服务**（`foregroundServiceType="connectedDevice"`，Android 14+ 规范类型），通知栏常驻显示当前心率与时长；
- 断开自动重连：指数退避重试（如 1s / 2s / 4s / 8s，最多 5 次），超过阈值后通知用户手动重连；
- 适配小米后台限制：引导用户开启"自启动 / 后台运行 / 省电策略无限制"（小米系统弹窗引导）；
- 蓝牙权限：
  - Android 12+：`BLUETOOTH_SCAN`、`BLUETOOTH_CONNECT`（运行时申请）；
  - 旧版本：`BLUETOOTH`、`BLUETOOTH_ADMIN`、`ACCESS_FINE_LOCATION`（扫描兼容）。

#### 2.4 已知限制（需产品确认）

- 心率广播**必须由用户在手环端手动开启**，App 无法替手环开启；
- 广播在连接断开后可能自动关闭，需要用户重新开启；
- 实际广播频率与持续时长需真机实测（预期 1 次/秒）。

### FR3 运动记录

- 运动类型：跑步 / 骑行 / 步行 / 心率训练（不戴 GPS）/ 手动补录。
- 自动记录：
  - 来源 `gps`：户外运动，同时记录轨迹点、距离、配速（心率叠加待 FR2 恢复后支持）；
- 手动补录：来源 `manual`，用户填写时长、平均心率（或直接填消耗）、备注，用于没戴手环的运动。
- 列表：按日期展示运动记录，支持查看与删除。

### FR9 系统步数读取

#### 9.1 数据来源

- 使用硬件计步传感器 `TYPE_STEP_COUNTER`（系统级累计步数，**不依赖 Google 服务**，国产设备可用）。
- 传感器不可用时的降级：尝试 `TYPE_STEP_DETECTOR` 自累计；仍不可用则显示"设备不支持计步"，不阻塞其他功能。

#### 9.2 采集与存储

- 系统步数传感器只提供"开机以来累计值"，App 需要自己维护每日步数：
  - **策略（轻量档，推荐）**：
    1. App 打开/进入前台时读取累计值，与上次保存的基线做差，补入当天步数；
    2. WorkManager 每天定时（0 点 + 12 点）记录基线，保证跨天拆分；
    3. 每日步数写入 `daily_step_count` 表（date + steps）；
    4. 不常驻前台服务，通知栏干净，不受小米后台策略影响。
  - **升级路径（微信档，默认不做）**：如用户需要全天精确步数，再切为前台服务全时段监听（复用 RestTimerService 模式），代价是通知栏常驻 + 后台白名单引导。
  - 内存与电量：传感器监听本身开销极小（硬件低功耗计步），内存占用可忽略。
- 权限：`ACTIVITY_RECOGNITION`（Android 10+，运行时申请）。

#### 9.3 步数消耗估算（粗略）

```
步数消耗(kcal) ≈ 步数 × 0.0005 × 体重(kg)
```

- 仅作为"日常活动消耗"参考，UI 标注为粗略估算；
- 看板展示今日步数与估算消耗，近 7 天步数趋势；
- AI 评估与对话注入步数（如"今天走了 8000 步，约消耗 280 kcal"）。

### FR10 GPS 户外运动记录

#### 10.1 数据来源

- 使用原生 `LocationManager`（GPS + 网络定位融合），**不依赖 Google 服务**。
- 运动类型：跑步 / 骑行 / 步行，记录页选择后开始。

#### 10.2 采集与计算

- 采集：前台服务（`foregroundServiceType="location"`）按 1 秒 / 5 米策略采集经纬度、时间、海拔；
- 距离：相邻轨迹点 Haversine 距离累加；
- 配速：跑步/步行按 分/公里，骑行按 公里/小时；
- 轨迹点以 JSON 存入 `routeJson`（本期只存不画图，地图可视化后置）；
- 心率叠加：GPS 运动期间若米环 7 已连接，同时记录心率并参与消耗计算。

#### 10.3 权限

- `ACCESS_FINE_LOCATION` / `ACCESS_COARSE_LOCATION`（运行时申请）；
- 记录期间 App 通过前台服务运行，**不申请后台定位权限**（锁屏也能继续记录）。

### FR4 热量评估引擎

#### 4.1 基础代谢（BMR）—— Mifflin-St Jeor 公式

```
男性：BMR = 10×体重(kg) + 6.25×身高(cm) − 5×年龄 + 5
女性：BMR = 10×体重(kg) + 6.25×身高(cm) − 5×年龄 − 161
```

#### 4.2 运动消耗（心率法）—— Keytel 公式

```
男性：kcal/min = (−55.0969 + 0.6309×HR + 0.1988×体重(kg) + 0.2017×年龄) ÷ 4.184
女性：kcal/min = (−20.4022 + 0.4472×HR − 0.1263×体重(kg) + 0.074×年龄) ÷ 4.184
```

- 平均心率取整段记录的平均值；消耗 = kcal/min × 时长。
- 结果标注"估算值"，误差 ±20% 属正常。

#### 4.3 心率区间（可选增强，默认做）

- 最大心率 = 220 − 年龄（可换 208 − 0.7×年龄，实测后定）；
- 区间：50-60% 热身 / 60-70% 燃脂 / 70-80% 有氧 / 80-90% 无氧 / 90%+ 极限；
- 实时页面与记录详情展示区间占比，提升使用价值。

#### 4.4 每日热量口径

```
每日总消耗 ≈ BMR（静息） + 运动消耗（心率记录 + GPS 运动 + 步数估算 + 手动补录）
净摄入 = 当日饮食摄入 − 当日运动消耗
热量缺口/冗余 = 目标热量 − 净摄入
```

- 沿用 PRD 现有"目标热量"口径（增重场景下缺口为正表示需要多吃）；
- 负数表示热量冗余（超出目标/盈余）。

### FR5 看板展示

- "今日摄入"卡片升级为"今日热量评估"：
  - 摄入 / 目标
  - 运动消耗（+ BMR 参考值）
  - 净摄入
  - 缺口/冗余（带正负与颜色：缺口=鼓励多吃，冗余=提示盈余）
- 近 7 天热量柱状图增加"运动消耗"与"净摄入"维度（Vico 双系列）。

### FR6 AI 每日评估注入

- `buildDailyReviewContext()` 增加：
  - 今日运动消耗（来源明细：心率记录 N 分钟 / 手动补录）；
  - 净摄入与缺口（示例："今日摄入 2100，运动消耗 350，净摄入 1750，距目标 2800 还差 1050"）；
  - 近 3 天运动消耗统计。
- 评估时能识别"吃够但消耗多"的情况，给出更准确的增重建议。

### FR7 对话 Agent 路由扩展

- `IntentRouter` 新增"运动消耗/热量缺口"意图关键词：
  - 消耗类：消耗、运动消耗、跑了多少、心率、卡路里消耗；
  - 缺口类：缺口、盈余、净摄入、还剩多少热量；
- `UserContextBuilder` 对应查询 `ActivityRecord` 当日/近 3 天统计并注入。
- 测试：路由单测补充运动意图用例（目标新增 6-8 例）。

### FR8 数据模型

```kotlin
@Entity(tableName = "activity_record")
data class ActivityRecord(
    @PrimaryKey(autoGenerate = true) val id: Long = 0,
    val type: String,             // "running" / "cycling" / "walking" / "heart_rate" / "manual"
    val startTime: Long,          // 开始时间戳（毫秒）
    val durationMinutes: Int,     // 时长（分钟）
    val avgHeartRate: Int = 0,    // 平均心率（无心率时为 0）
    val maxHeartRate: Int = 0,    // 最大心率
    val caloriesKcal: Int,        // 估算消耗
    val distanceMeters: Double = 0.0, // GPS 距离（米）
    val avgPace: String? = null,      // 配速文本（如 "5'30\""）
    val routeJson: String? = null,    // 轨迹点 JSON（地图后置）
    val source: String,           // "band_heart_rate" / "gps" / "manual"
    val note: String? = null      // 备注（如：跑步、骑车）
)

@Entity(tableName = "daily_step_count")
data class DailyStepCount(
    @PrimaryKey val date: String, // "yyyy-MM-dd"
    val steps: Int,
    val caloriesKcal: Int
)
```

- 新增 `ActivityRecordDao`（按日期查询/汇总、插入、删除）与 `DailyStepCountDao`；
- AppDatabase 升 **v6**，schema 导出；开发期沿用 destructive fallback（发布前补 Migration，见中期文档 D4）。

## 五、风险与缓解

| 风险 | 等级 | 缓解 |
| :--- | :--- | :--- |
| 心率广播需手动开启、可能自动关闭 | 高 | 清晰的引导弹窗与状态提示；记录页显示"等待广播"状态 |
| BLE 连接不稳定（小米系统后台限制） | 中高 | 前台服务 + 自动重连 + 后台白名单引导 |
| GPS 前台服务耗电较大 | 中 | 结束后立即停止；记录页显示预估耗电提示；轨迹抽稀存储 |
| 定位权限被拒绝 | 中 | 无定位时降级为"心率训练"记录，不阻塞使用 |
| 步数传感器可用性差异 | 中 | TYPE_STEP_COUNTER 缺失时降级 TYPE_STEP_DETECTOR；再不可用则隐藏步数入口 |
| 心率公式误差（±20%） | 中 | UI 标注估算值；可后续用手动输入校准 |
| 米环 7 实际广播格式/频率与预期不符 | 中 | Phase 2 先做 1 天真机验证再铺开 UI |
| 档案默认值导致计算偏差 | 低 | 首次使用评估功能时强制引导填写年龄/性别 |

## 六、验收标准

1. 档案填写年龄、性别后，看板能显示 BMR 与运动消耗估算。
1. 档案填写年龄、性别后，看板能显示 BMR 与运动消耗估算。
2. 开启 GPS 跑步记录 5 分钟后结束，记录的距离与配速合理（与导航软件对比误差可接受），轨迹点已入库。
3. 看板显示今日系统步数与步数消耗；连续两天记录后近 7 天步数趋势正确。
4. 手动补录一条 300 kcal 后，净摄入与缺口同步更新。
5. AI 每日评估能引用运动消耗并指出净缺口（如"吃了 2100、消耗 350、净缺口 1050"）。
6. 对话问"我今天消耗了多少""今天走了多少步"能基于本地记录精确回答。
7. GPS 记录中锁屏后仍持续采集；App 不崩溃。
8. 路由单测覆盖运动消耗/步数/缺口意图（新增用例全部通过）。
9. （延期项）米环 7 心率连接与心率消耗计算，待 FR2 恢复后验收。
