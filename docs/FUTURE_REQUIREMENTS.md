## 一、P0 缺陷修复需求

### D1 数据导入修复（数据安全，最高优先级）

- **现状**：导入逻辑只执行 `deleteAll()`，解析出的 JSON 被丢弃，未写入任何记录（DashboardViewModel.kt:124、SettingsViewModel.kt:116）。
- **需求**：
  1. 解析备份 JSON 后，按表（饮食/训练/体重/聊天/食物库/动作库）批量插入；
  2. 保留原始记录的主键、时间戳、图片路径字段；
  3. 导入前校验 JSON 格式与结构，格式非法时提示错误且**不得清空现有数据**；
  4. 导入全过程放入数据库事务（Room `withTransaction`），失败整体回滚；
  5. 收敛两套重复的导入导出逻辑（Dashboard 与 Settings），统一到数据层 Repository。
- **验收**：导出 → 清空数据 → 导入，全部记录完整恢复；粘贴非法 JSON 不破坏现有数据。

### D2 数据导出修复

- **现状**：直接写 `Environment.getExternalStoragePublicDirectory(DIRECTORY_DOWNLOADS)`，在 targetSdk 30+ 下无权限不可写。
- **需求**：
  1. 改用 MediaStore（`Downloads` 集合）或 SAF 文件创建器（`ActivityResultContracts.CreateDocument`）；
  2. 保留中文文件名 `增重助手备份_日期.json`；
  3. 导出包含全部数据表 + 导出时间/版本字段，便于后续兼容。
- **验收**：真机点击导出成功，文件可在系统文件管理器中打开，内容为合法 JSON。

### D3 编辑记录保留原始时间

- **现状**：编辑饮食记录时 `timestamp` 重置为当前时间、`imagePath` 置空；编辑训练记录时 `date` 重置为今天（DietViewModel.kt:162、TrainingViewModel.kt:322）。
- **需求**：
  1. 编辑时保留原 `timestamp`/`date`/`imagePath`；
  2. DAO 提供 `@Update` 方法（当前用 `insert(REPLACE)` 模拟更新），按主键更新字段；
  3. 两处 ViewModel 的 `updateRecord` 改为调用 `@Update`。
- **验收**：编辑一条昨天的记录并保存后，记录仍归属昨天，图片仍可显示。

### D4 数据库迁移方案

- **现状**：AppDatabase version=4，无任何 Migration，`fallbackToDestructiveMigration(false)` 导致 schema 变更时升级闪退（AppDatabase.kt:61）。
- **需求**：
  1. 开启 `exportSchema = true`，schema JSON 纳入版本管理；
  2. 编写 version 1→2→3→4 的完整 Migration 并注册；
  3. 开发期临时方案可改为 `fallbackToDestructiveMigration()`（清库重建），但**发布前必须替换为真实 Migration**；
  4. 后续每次改表同步补 Migration。
- **验收**：用旧版本 APK 写入数据后安装新版本，数据完整、无闪退。

### D5 AI 识别失败流程优化

- **现状**：识别失败时同时置 `RecognitionState.Error` 并跳转空结果确认页，错误卡片残留。
- **需求**：
  1. 识别失败时**留在饮食主页**，显示错误提示（可点击"转手动录入"）；
  2. 仅识别成功才跳转 FoodConfirmScreen；
  3. 错误提示提供关闭入口，进入确认页前自动清除。
- **验收**：断网/无效 Key 拍照后，页面展示明确错误，不跳转空页面；点击手动录入可正常记录。

### D6 数字输入框可清空

- **现状**：FoodConfirmScreen 重量/热量输入使用 `toIntOrNull()?.let{}`，清空输入框时状态不更新（FoodConfirmScreen.kt:117）。
- **需求**：允许输入框清空并保存中间字符串，保存/计算时再做数值校验；空值按 0 或提示处理。
- **验收**：用户可全选删除后重新输入任意数值，光标不跳回。

## 二、P1 核心缺失功能需求

### F1 AI 每日综合评估（PRD 模块四，整体未实现）

- **入口**：看板页新增"今日综合评估"按钮。
- **逻辑**：
  1. 本地查询今日饮食明细、今日训练明细、近 3-5 天体重记录；
  2. 组装上下文：**近 3 天给详细数据，更早数据只给本地 SQL 算好的统计值**（平均体重、总热量、训练频率）；
  3. 调用文本模型，System Prompt 为专业增肌教练（CSCS），要求 200 字以内；
  4. 结果存入 `AdviceLog` 表（`requestSnapshot` + `aiResponse`）；
  5. 提供历史评估查看页/列表。
- **验收**：设置目标 2800kcal、当日摄入 2100kcal 时，评估能指出热量缺口并给出加餐建议；历史记录可回看。

### F2 对话 Agent 本地意图路由 + 精准数据注入（PRD 模块五） ✅ 已完成 2026-08-06

- **目标**：拒绝全量投喂，改为"本地路由、按需查询"。
- **需求**：
  1. 在 `domain/router` 实现意图识别引擎：基于关键词/正则，至少识别以下意图：
     - 热量类（"今天/最近吃了多少热量"）→ 查 DietRecord 当日/近 3 天总和与明细；
     - 动作类（"深蹲重量进步了吗"）→ 查 TrainingRecord 指定动作历史（DAO 已有 `getRecordsByExerciseName` / `getRecentRecordsByExercise`）；
     - 整体趋势类（"最近怎么样"）→ 近 3 天精简摘要 + 30 天平均体重/热量统计（SQL 计算）；
     - 闲聊/未命中 → 不带数据直接回复；
  2. 将查到的精准数据以"用户近期数据：..."文本拼入 System Prompt 之后，不注入无关历史；
  3. 长短期记忆分层：近 3 天详细、7 天以上仅统计值，严禁原始数据/聊天记录投喂；
  4. 保留现有滑动窗口（最近 10 条）；
  5. 路由引擎需要单测覆盖（关键词命中/未命中/组合意图）。
- **验收**：
  - 问"我最近三天吃了多少热量？"→ 基于实际记录给出精确数值；
  - 问"我深蹲重量进步了吗？"→ 提取近期深蹲数据分析趋势；
  - 闲聊问题不带数据也能正常回答。

### F6 休息倒计时增强（PRD 模块二）

- **需求**：
  1. 倒计时结束播放系统提示音（ToneGenerator 或系统通知铃声）；
  2. **后台常驻**：计时状态提升为前台服务或 WorkManager + 通知栏倒计时，退出训练页/锁屏后继续计时；倒计时结束发通知并震动；
  3. **HyperOS 焦点通知适配**：利用高优先级通知模拟"灵动岛"效果（PRD 已列，评估实际可行性后实现）；

- **验收**：开始倒计时后退出页面/锁屏，通知栏持续显示剩余时间，结束时震动并收到提示。

## 五、验收标准（更新版）

在 PRD 第 10 节九条验收基础上，新增：

1. **备份恢复闭环**：真机导出 → 删除数据 → 导入，饮食/训练/体重/聊天记录完整恢复；非法文件导入不破坏现有数据。
2. **编辑不串日期**：编辑任意历史记录，保存后归属日期与图片不变。
3. **升级不闪退**：旧版本数据可平滑升级到新版本。
4. **每日评估可演示**：今日摄入低于目标 80% 时，评估明确指出热量缺口。
5. **对话路由可演示**：热量/动作/整体趋势三类问题均基于本地数据精确回答，聊天历史仅发送最近 10 条。
6. **模板可闭环**：保存模板 → 一键填充 → 保存记录。
7. **小组件可用**：桌面可添加小组件，内容随数据更新。
8. **测试覆盖**：P0 修复均有对应单测；路由引擎至少 10 个用例。
